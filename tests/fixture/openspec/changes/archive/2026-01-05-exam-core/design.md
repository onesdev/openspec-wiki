# 设计：考试核心能力

## Context

平台此前没有考试实体，题目与账号各自独立。判分结果需要归属主体，考生需要「可见考试」的入口。考试状态既要表达「未发布不可见」，又要表达「已结束不可再提交」。

## Decisions

### D1 状态用固定枚举 + 单向推进，不做可配置状态机

- `status` 列以 `CHECK(status IN ('draft','published','closed'))` 约束取值，接口层再校验一次。
- 只允许 `draft → published → closed`，不允许回退。
- 理由：三态已覆盖真实业务（未发布 / 进行中 / 已结束），可配置状态机在没有多租户需求前是纯负担。
- 拒绝的备选：单独建 `exam_status` 字典表。收益是状态可扩展，代价是每次查询多一次 join，且当前无扩展需求。

### D2 考生可见性由状态推导，不单独维护可见名单

- 「我的考试」直接按 `status IN ('published','closed')` 过滤，不建 `exam_visibility` 关联表。
- 理由：当前所有考生可见同一批已发布考试，没有按人下发试卷的需求。
- 风险：未来若要做定向发卷，需要新增关联表并改造查询——届时应作为一次明确的迁移，而非预留模糊的扩展点。

## Non-Goals

- 不引入考试模板与考试复制：模板会让「考试」与「题包」的边界模糊，而题目本身已是可复用单元。
- 不做定时自动开考与自动收卷：依赖后台调度器，与「状态由管理员手动推进」的简单模型冲突。
- 不做多租户隔离：当前为单机构部署，隔离需求尚未出现。
