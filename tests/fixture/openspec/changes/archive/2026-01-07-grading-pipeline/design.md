# 设计：判分流水线

## Context

判分引擎本身对用例数没有要求，但成绩存储把 20 当成隐含前提。同时 `saved_codes` 的唯一键不含语言，导致同一道题换语言提交会覆盖上一份代码。

## Decisions

### D1 用例数取题包实际条数，不设固定值

- 判分入口以 `total = len(cases)` 计算，得分 `round(passed / total * 100)`。
- 理由：固定值会让轻量题目被迫凑满用例，出题与判分耗时都被无谓放大。
- 风险：3 条用例时得分粒度变粗（0 / 33 / 67 / 100）。接受该粒度，前端以「通过用例 x / y」明细补偿信息损失。

### D2 唯一键扩到含语言的整表重建

- SQLite 不支持修改唯一键，只能建 `saved_codes_v2` → 拷数据 → `DROP` 旧表 → `RENAME` 回 `saved_codes`。
- 理由：`saved_codes` 的读写接口保持不变，重建对上层透明。
- 拒绝的备选：保留旧唯一键，把语言编码进 question_id。会污染主键语义，且无法再按语言单独查。
- 风险：迁移期间若进程中断，可能留下 `saved_codes_v2` 残表；迁移脚本对 `DROP` / `RENAME` 的先后顺序敏感。

## Non-Goals

- 不引入小数分或加权计分：粒度信息由「通过用例 x / y」表达，分数只作粗筛。
- 不做判分结果的实时推送：判分是同步短任务，轮询即可满足。
- 不迁移存量 `saved_codes` 之外的历史数据：其他表未受唯一键变更影响。
