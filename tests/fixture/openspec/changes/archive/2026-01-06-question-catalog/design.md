# 设计：题库浏览与详情

## Context

题库列表与详情共用大部分字段，但详情多出「引用了哪个 SQL 题库」这一信息。该信息由 `database_uid` 指向 `databases.uid`，展示时需要库名而非 uid。

## Decisions

### D1 `database_uid` 取字符串 uid 而非自增主键

- `questions.database_uid` 存 `databases.uid`（字符串），不存 `databases.id`。
- 理由：题包导出 / 导入时主键必然失效，uid 才是可跨库稳定引用的标识。题库随题包一同迁移时，uid 保持不变即可保持引用关系。
- 拒绝的备选：存自增主键并靠外键约束。外键在导入流程里需要额外的重映射，收益不足以抵消复杂度。

### D2 `database_name` 由附加查询补全，不做联表

- 详情接口先取题目行，再按 `database_uid` 查一次题库名，拼进响应。
- 理由：题目绝大多数不引用题库（`database_uid` 为空），联表会让所有详情请求都多付一次 join 的成本。
- 风险：响应字段由两处拼装，读代码时需要跟到第二个查询才能看全字段——文档页必须显式标注该字段的来源。

## Non-Goals

- 不在题库内做全文检索：题目量级在千以内，浏览器端过滤足够，引入 FTS 是过度设计。
- 不提供题目批量导出：导出单位是题包而非单题，批量导出会绕开题包的校验链路。
- 不引入题目标签体系：标签需要独立的关系表与维护界面，当前用题型 + 标题前缀已能满足查找。
