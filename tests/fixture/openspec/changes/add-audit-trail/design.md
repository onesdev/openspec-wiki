# 设计：操作审计流水

## Context

平台需要知道「谁改了什么」。写入路径集中在账号管理与题库编辑两处，读取路径是一个按条件过滤的列表页。审计数据只增不改，且不参与任何业务判断。

## Decisions

### D1 审计写入与业务写入同事务，不做异步

- 审计条目与业务变更写在同一个事务里，业务成功才留痕。
- 理由：异步写入会丢条目（进程崩溃时队列未落盘），而审计的价值恰恰在于「一定记得住」。写入量是人工操作级别，事务开销可忽略。
- 拒绝的备选：投递到消息队列异步落库。需要引入 MQ 组件与消费者进程，为一个低频写入场景引入一整套运维负担。

### D2 只记写操作，不记读操作

- 审计覆盖新增、修改、删除；查询与浏览不留痕。
- 理由：读操作量级高两个数量级，记录会让流水表迅速失去可读性。合规关注的是「变更」而非「查看」。

## Non-Goals

- 不做审计日志的导出与归档：当前数据量在十万条以内，单表查询足够；归档策略等触及量级上限时再定。
- 不做操作回滚：审计是事实记录而非事务日志，回滚需要完整的前后镜像，超出本变更范围。
- 不记录读操作：见 D2。

## Open Questions

- 审计流水保留多久？当前无上限，待合规口径明确后补。
